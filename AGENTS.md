## UI and maintenance conventions

Follow the owner-adopted [Himmah design system](docs/DESIGN_SYSTEM.md) for every existing and future UI implementation. Read it before UI work, alongside the [Airbnb research](docs/redesign/AIRBNB_DESIGN_RESEARCH.md). This standing preference supersedes earlier exact visual values: retain Himmah leaf/forest identity with the adopted warm neutral surfaces, system typography, compact rows and restrained cards. Real bookmarkable routes reload independently. Navigation: People, Activities, Insights, Manage; learning contextual to activities; language/account settings in Profile. Compact organization switcher and phone navigation. Use TanStack Query keys scoped by user/org/filter; growing lists use cursor/infinite pagination, stable timestamp+ID order, 25 default/50 maximum and accessible manual Load more. Skeleton page loading; action-local disabled spinner for pending mutations. Fixed square icon menus for secondary actions; Lucide labels, 44px touch targets, keyboard-aware scrollable forms and visible focus. Destructive actions/sign-out use accessible confirmation dialogs. Reuse shared primitives/focus/viewport helpers. Localize all shipped text/errors in EN/NL/TR, resolving messages within render/request.

Keep service-worker caches public-only: never cache authenticated HTML, auth/API/private records or queue mutations offline. Clear private caches on sign-out/scope loss. Keep secrets server-only and exclude them from Git/logs/screenshots. Preserve Cloudflare native fetch receiver wrappers and managed-auth proxy/error handling; auth changes require actual Workerd regression tests.

Owner list consistency: use the adopted shared directory layout for Contacts, Groups, Staff, Invitations and Staff assignments. Reuse `directory-layout.tsx` and the shared directory CSS for headings, search bars, compact avatar rows and square secondary actions. Apply page padding once in OrganizationPortal; do not add narrower, independently padded People wrappers. Contact/group rows are full-row navigation links. Resolve staff display names from current managed account profiles with stored-name fallback; never render account IDs as names. Preserve this pattern for future list pages.

Owner UI refinement: informational cards should be compact, with one layer of padding rather than stacked card/content padding. Contextual section-add actions use a fixed 44px icon control on phones with a localized accessible name; show the text label on wider screens. Reuse the shared compact Card density where appropriate.

Owner form focus: do not autofocus fields or page headings when opening forms. Keep normal keyboard navigation, focus trapping and restoration on sheet dismissal.

Owner form presentation: complex workflows use independently reloadable pages; simple forms use the shared shadcn/Vaul bottom sheet. Follow [form classification](docs/FORMS.md), `FormSurface` and `PeopleForm`; never introduce a centered dialog for an input workflow. Keep confirmations in accessible alert dialogs. Preserve unsaved-change guards, one confirmation per leave action, failed-save drafts/request identity, current tenant authorization, version snapshots, localized labels, keyboard-aware sizing, safe areas and focus restoration. Page return links preserve the originating filters and must remain in the current organization.

Owner-approved child-list pattern: contact profiles show at most three rows per collection, an SQL total count and a real View all link. Full lists live on independently reloadable routes with their own infinite pagination and URL-backed search/history filters. Do not put auto-expanding infinite lists or nested scroll areas inside entity overview sections. Keep preview/full query caches separate. Form pickers keep bounded pagination within their page or sheet.

Owner-approved registration: session reservations and attendance are independent. Follow [registration behavior](docs/REGISTRATION.md): optional drop-in by default; required sessions derive expected contacts from confirmed reservations, freeze the original at check-in opening and audit later amendments. Enforce capacity under session locks, current scoped permissions, immutable events/receipts, snapshot versions and reasoned cancellation. Owner card action hierarchy: each entity card has at most one prominent primary action button. Put secondary actions in the shared square ItemActions menu or use compact secondary controls when context requires. Activity/session list cards use View as primary; session detail uses attendance as primary with registrations in the more menu. Informational cards may have no primary action; form Save/Cancel and confirmation choices are workflow exceptions. Do not stack multiple full-width action buttons on a card.

Owner-approved pricing increment: follow docs/PRICING.md. Correcting an incorrect receipt is owner/admin-only, reasoned and append-only; it is not a refund or charge waiver. No inferred money from attendance, no offline financial writes, no full receipt/history or organization cash totals for scoped collectors.

Owner design preference: unify typography, spacing, surfaces, shape, state and motion through theme tokens and shared components. Update affected existing patterns when changing a feature; future implementations must follow docs/DESIGN_SYSTEM.md. Do not add page-local palettes, repeated override stylesheets, oversized stacked card actions or duplicated padding. Keep the documented form, accessibility, translation, pagination, permission and financial behavior.

Owner unified session management: show present contacts and payment management together, with compact present/paid/unpaid stats on session detail and more detailed scoped counts/amounts in management. Support selection of one or up to 50 contacts for add/remove/paid/unpaid. The add picker includes present contacts visibly greyed out and disabled. Correction is not a physical refund. Cash scope is required to clear recorded money, including on removal. Keep the current present-only list, registration independence, no autofocus, professional compact design and scoped privacy. See docs/CASH.md.
