# Organization onboarding — early access

## What is implemented

`/start` is the organizer portal, reached from the public landing page at `/`. Both support English, Dutch and Turkish. Adult organizers can create an account, request an email verification code, verify it, sign in/out, restore their session, and use email-code password recovery. Verified organizers can create a workspace (name, unique address and timezone), list their memberships and return to a saved workspace. There is no paid checkout yet.

Organization setup is persistent. No demo, mock engagement controls or planned-feature panels are exposed in the deployed UI. Saved workspaces show their organization details and, for owners/admins, the persistent member/group directory and staff invitation controls. Roster records do not create logins. Activities, attendance, points, periods, scoped volunteers and rewards are implemented. Participant access now uses separate consent-attested invitations and a private read-only dashboard; see [Participant access](PARTICIPANT_ACCESS.md).

## Backend and isolation

The Cloudflare Worker runs TanStack Start SSR, serves built client assets and handles `/api/*`. A small allowlisted same-origin proxy uses the Neon managed auth service; no passwords are stored by Himmah. The SDK remains the Neon wrapper. Auth cookies are scoped to the app host, sessions are checked against the managed service without cookie-cache reuse, and private API responses use `Cache-Control: no-store`.

`GET /api/account` requires a valid session. `GET /api/organizations` selects memberships for the verified user only. `GET /api/organizations/:id` joins membership and organization and returns 404 for unauthorized IDs. `POST /api/organizations` requires a verified email, same-origin JSON request and a valid input including explicit adult organization-management authorization. Ownership is derived from the session, never client role/user IDs. Every create operation has a UUID creation key. Organization plus owner membership are created atomically; retries for the same user/key return the same organization. Unique slugs prevent duplicate addresses.

Mutations use a Cloudflare rate-limit binding (10 attempts per minute per auth IP or workspace-creation user key; approximate edge enforcement). Managed auth has its own limits. The proxy does not expose admin auth endpoints, generic redirects, social OAuth or arbitrary upstream hosts. No billing license grants authorization.

## Database and migrations

Drizzle schema: `src/server/schema.ts`. Generated migration and metadata: `db/migrations/generated/`. Initial tables are `hub_organizations` and `hub_memberships`, with UUID organization keys, membership composite primary key, organization foreign key and checked roles. A unique creator/request key enforces organization-creation idempotency.

Migration generated by `drizzle-kit generate`, then transported verbatim through the connected Neon SQL transaction tool because CLI direct database access is restricted in this environment. Standard `drizzle.__drizzle_migrations` SHA-256 hash/timestamp records are included atomically. Applied first to development, then the dedicated onboarding branch. Main was not migrated. Future migrations must continue from this Drizzle history.

The onboarding branch is not a disposable development branch: it can contain organizer accounts and organizations. Never reset/clone its records into sample environments. Never seed synthetic participant records or perform live enrollment as a test.

## Configuration and local development

Cloudflare non-secret vars: `HIMMAH_AUTH_URL`, `HIMMAH_APP_ORIGIN`. Dedicated Worker secret: `HIMMAH_DATABASE_URL` for the onboarding branch only. Never assign shared workspace database/auth variables or reuse Kermes Pay credentials. Do not expose the connection string to Next public environment variables.

`npm run dev` serves the TanStack Start application and Worker API through Vite/Cloudflare. `npm start` previews a completed build. That needs a project-local ignored `.dev.vars` with a dedicated development database/auth setup, and an explicit localhost app-origin override; the production origin does not authorize localhost mutations. Do not copy onboarding credentials into test fixtures or source files.

Neon shared SMTP is suitable for early-access testing; production-branded email delivery, abuse monitoring, legal/privacy information and support/account recovery processes need completion before general rollout. No real registration/email-delivery browser test has been performed from this restricted workspace unless subsequently recorded below.

## Client/proxy error handling

The installed Neon adapter throws normalized AuthApiError objects for non-2xx responses, including snake_case codes. UI handles these with authFailure as well as Better Auth returned error objects. Do not display raw provider errors or hide all failures behind one generic message. Account creation and verification email delivery are separate outcomes; delivery failure must not encourage duplicate signup. Password requirements are visible and validated (12–128 characters).

The same-origin proxy sets x-neon-auth-middleware=true, forwards the SDK client-info/user-agent headers, and supplies the configured Origin/Referer after validating the browser request origin. This follows the installed managed SDK server-proxy contract while retaining endpoint allowlisting and rate limits. Rate-limited proxy responses include a stable code/message understood by the real SDK. Regression tests use the actual client against our actual proxy with a fake upstream; they are not proof of live provider signup or email delivery.


## Confirmed runtime fix after the signup screenshot

Cloudflare’s global fetch requires its original receiver. The former `deps.fetch = globalThis.fetch` default was invoked as `deps.fetch(...)`, which threw “Illegal invocation” inside Workerd before reaching Neon. The generic catch turned it into the service-unavailable message. A forwarding arrow now preserves the receiver. This affects both signup proxy calls and authenticated session lookups. No identity migration is necessary.

`npm run test:worker` bundles the actual API and runs it in Workerd with a second local Worker as the upstream fixture. It proves the old default returns 503 and the repaired default supports signup/verification/session lookup while retaining cookie scoping, no-store responses and CSRF checks. This runtime test complements the SDK/component tests; none sends a real verification email or uses the screenshot’s account details.
