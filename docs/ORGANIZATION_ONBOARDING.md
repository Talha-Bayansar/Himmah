# Organization onboarding — early access

## What is implemented

`/start/` is a separate organizer portal alongside the fictional demo at `/`. Adult organizers can create an account, request an email verification code, verify it, sign in/out, restore their session, and use email-code password recovery. Verified organizers can create a workspace (name, unique address and timezone), list their memberships and return to a saved workspace. There is no paid checkout yet.

Organization setup is persistent. The attendance, activities and youth records in the demo remain fictional/browser-memory-only and are NOT linked to saved workspaces. The saved-workspace welcome screen explains that member invitations and persistent Hub activity management are the next work. Do not enroll real children yet.

## Backend and isolation

The Cloudflare Worker serves static Next.js assets and handles `/api/*`. A small allowlisted same-origin proxy uses the Neon managed auth service; no passwords are stored by Himmah. The SDK remains the Neon wrapper. Auth cookies are scoped to the app host, sessions are checked against the managed service without cookie-cache reuse, and private API responses use `Cache-Control: no-store`.

`GET /api/account` requires a valid session. `GET /api/organizations` selects memberships for the verified user only. `GET /api/organizations/:id` joins membership and organization and returns 404 for unauthorized IDs. `POST /api/organizations` requires a verified email, same-origin JSON request and a valid input. Ownership is derived from the session, never client role/user IDs. Every create operation has a UUID creation key. Organization plus owner membership are created atomically; retries for the same user/key return the same organization. Unique slugs prevent duplicate addresses.

Mutations use a Cloudflare rate-limit binding (10 attempts per minute per auth IP or workspace-creation user key; approximate edge enforcement). Managed auth has its own limits. The proxy does not expose admin auth endpoints, generic redirects, social OAuth or arbitrary upstream hosts. No billing license grants authorization.

## Database and migrations

Drizzle schema: `src/server/schema.ts`. Generated migration and metadata: `db/migrations/generated/`. Initial tables are `hub_organizations` and `hub_memberships`, with UUID organization keys, membership composite primary key, organization foreign key and checked roles. A unique creator/request key enforces organization-creation idempotency.

Migration generated by `drizzle-kit generate`, then transported verbatim through the connected Neon SQL transaction tool because CLI direct database access is restricted in this environment. Standard `drizzle.__drizzle_migrations` SHA-256 hash/timestamp records are included atomically. Applied first to development, then the dedicated onboarding branch. Main was not migrated. Future migrations must continue from this Drizzle history.

The onboarding branch is not a disposable development branch: it can contain organizer accounts and organizations. Never reset/clone its records into sample environments. Youth data is not accepted in this milestone.

## Configuration and local development

Cloudflare non-secret vars: `HIMMAH_AUTH_URL`, `HIMMAH_APP_ORIGIN`. Dedicated Worker secret: `HIMMAH_DATABASE_URL` for the onboarding branch only. Never assign shared workspace database/auth variables or reuse Kermes Pay credentials. Do not expose the connection string to Next public environment variables.

`npm run dev` serves the static UI in Next but does not provide the Worker API. For an integrated local app, build then use `npm start` (Wrangler). That needs a project-local ignored `.dev.vars` with a dedicated development database/auth setup, and an explicit localhost app-origin override; the production origin does not authorize localhost mutations. Do not copy onboarding credentials into test fixtures or source files.

Neon shared SMTP is suitable for early-access testing; production-branded email delivery, abuse monitoring, legal/privacy information and support/account recovery processes need completion before general rollout. No real registration/email-delivery browser test has been performed from this restricted workspace unless subsequently recorded below.

## Verification

Automated tests cover input validation, unauthenticated access, email verification requirement, CSRF origin enforcement, retry-safe creation, role spoofing, cross-user list/detail isolation, slug conflicts, rate limiting, proxy allowlisting/cookie handling and non-disclosure of upstream errors. These use a test identity and store; they do not prove email delivery or browser cookie behavior against the managed service.

Database migration/constraint checks and Cloudflare build/deployment are verified separately. Direct access to the workers.dev app and Neon Auth host is restricted by the workspace network; browser signup/session restoration/email delivery must be confirmed through the phone-testing flow. Do not describe mock identity tests as live end-to-end verification.
