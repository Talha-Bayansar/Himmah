# Permanent activity deletion

Owner-authorized 30 October 2026. Archive remains a non-destructive organizational action and keeps participation/payment history in Insights. Owner/admin may separately choose **Permanently delete** in an active or archived activity's shared more menu. Volunteers cannot preview or delete.

The application fetches a current authorized preview: activity name, sessions, attendance records, charges and payment receipts. One destructive confirmation explains irreversible removal, preservation of contacts/groups, the archive alternative and that deleting tracking records does not refund money. Cancel writes nothing. No input form or autofocus is introduced.

Deletion removes the entire activity subtree: sessions, current attendance and history, registration/settings/expected rosters/history, principal charges, payment receipts/allocations/corrections/reversals, command/request receipts, activity-specific staff assignments and their history, linked notifications/deliveries and related directory audit entries. It never removes contacts, groups, group membership, staff accounts or organization membership. Unexpected cross-activity financial relationships fail closed. Foreign keys remain enforced.

The verified API accepts an administrator-only GET preview and DELETE on `/api/organizations/:org/activities/:activity`; preview uses `?deletionPreview=true`. Both are rate limited and no-store. Server-side authorization precedes every read/write/replay. SQL independently checks current owner/admin membership, locks membership, activity and ordered sessions, and compares a hash of the reviewed subtree before deleting. Changed data produces a conflict and requires a fresh preview and confirmation. A failed command leaves all rows intact. No mutations are queued offline.

`activity-deletion.sql` provides scoped helpers and `hub_delete_activity`. Historical update/delete guards remain enabled. They permit only DELETE of the matching rows during the administrator's transaction-local deletion context, while the root activity still exists. All normal history writes/deletes remain forbidden. Indexed tenant/activity/relationship predicates bound preview/deletion reads. No global replication setting, trigger disabling, schema drop, cascading table deletion or security-definer privilege is used.

A random request key and snapshot hash survive uncertain network errors in the mounted page. Exact retry returns the original outcome, even after the activity is gone; conflicting key reuse fails. Current administrator access is rechecked before replay. A minimal administrative deletion receipt remains in `hub_directory_audit` (actor, activity ID, request ID, snapshot hash and timestamp); it retains no participant or financial payload. Deleted business data does not appear in reporting. Success returns to Activities, cancels in-flight scoped reads, clears deleted/report caches and refreshes lists/Home/Insights. Archive behavior and report definitions are unchanged.

Fresh installation includes the function file. Existing verified Himmah targets use `scripts/activity-deletion-plan.mjs`, a guarded, digest-recorded transaction. Deployment and validation evidence belongs in [infrastructure history](INFRASTRUCTURE.md).
