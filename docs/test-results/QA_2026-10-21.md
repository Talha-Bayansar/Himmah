## Open findings

### QA-01 — viewed club resets when changing game tabs

Priority: medium UX. Reproduced in Club Manager league/tournament and Team Play league/tournament as an organizer.

1. Open a synthetic season's clubhouse with multiple clubs.
2. Select a club other than the default, for example Nur (third entry).
3. Open Squads through bottom navigation.
4. Wait for the Squads heading, then inspect the selection and reload.

Expected: the selected club remains the viewing context across tabs and reloads.

Observed: the destination URL drops the `club` search parameter. The displayed club changes to the default (Atlas in the organizer fixture), and remains there after reload. A direct reload of a URL that still contains `club` preserves it; the loss occurs during navigation. No saved club, assignment, rating or match data changes.

The responsible navigation links pass organization/season params but omit the club search context: [ArenaNavigation](../../src/futsal/FutsalExperience.tsx#L114). Recommended correction: carry the validated club parameter across game navigation, then add an assertion that waits for the destination heading and checks selection after reload. Reading the select immediately after clicking can falsely report success while the old screen is still mounted; the audit explicitly waited for the destination.

Status: **open; not changed in this testing-only audit**.

### QA-02 — cancelled season can be labelled active in the organizer game UI

Priority: medium UI/status clarity. Reproduced in all four mode/format combinations using an organizer fixture with a cancelled setup and retained active game state.

1. Use a cancelled synthetic season (do not cancel a real season solely to reproduce this).
2. Open its organizer Competition route directly.
3. Compare the setup's cancelled status with the competition banner.

Expected: the game UI clearly identifies cancellation and does not imply that scheduled play is continuing.

Observed: the banner says “Season active,” with no cancelled label. The new experience derives that label from game state and does not account for setup cancellation: [competition banner](../../src/futsal/FutsalExperience.tsx#L536). The separate season list correctly identifies cancellation.

An additional local PostgreSQL/API scenario activated a synthetic game, cancelled its setup and attempted a due event. The API returned **409**, game version remained unchanged, and the game GET response explicitly returned `cancelled: true`. Thus cancellation enforcement works; the new display ignores that status. Participant access to cancelled seasons remains denied by the current query policy.

Recommended correction: combine setup cancellation with game-state presentation; suppress misleading next-event prompts and clearly retain historical results. Add a cancelled-season game-view regression.

Status: **open; not changed in this testing-only audit**.

## Boundaries and intentional behavior

- Tests used disposable local PGlite databases and intercepted synthetic browser APIs. No real organization, account, participant, season, point award, reward or notification was created or changed.
- The browser matrix used Chromium with phone/tablet viewport emulation. It does not prove physical iOS/Android behavior or complete WCAG compliance. The contrast check covers production button CSS, not every rendered color combination.
- Separate PWA identities, icons and splash dimensions pass automated checks. Actual dual installation, OS splash rendering, physical keyboard behavior and real-device push delivery still need a phone check.
- Live signup/email-provider delivery and signed-in hosted database connectivity were not exercised in this audit. Direct workers.dev access is restricted in this environment; no bypass was used.
- Training/matches remain organizer-triggered when due. Automatic game scheduling, tactics/lineup changes and automatic prize handouts are not implemented. These are documented product boundaries, not newly discovered defects.
